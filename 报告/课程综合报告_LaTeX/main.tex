\begin{abstract}
本报告对应第二周综合设计阶段，重点记录在 \verb|sobel_05_pc_control_display| 基础上完成的上位机控制显示、显示模式切换、阈值调节、彩色叠加以及输入格式扩展。第一周的 RTL 仿真、HDMI 固定图案、HDMI Sobel、UART 图像显示和 UART Sobel 显示已经在仿真报告与初步实验报告中提交，本文只把它们作为实验五的前置基础，不再重复展开。

实验五的基础部分实现了 PC 上位机通过 UART 发送图像和控制命令，PS 端解析图像帧与控制帧并写入 BRAM，PL 端读取 BRAM 图像后完成灰度、Sobel、原图/灰度/边缘/叠加显示模式选择，最后通过 HDMI 输出到显示器。综合扩展部分选择“基于 sobel\_05 的上位机与输入规格扩展”，实际完成重点放在上位机侧：在保留原有显示控制命令的前提下，扩展图片输入方式，使上位机能够读取新增图片格式并统一预处理为 FPGA 工程支持的 RGB888 图像帧，再通过原 UART 协议送入开发板。报告中给出设计方案、关键代码思路、仿真/上板结果、资源占用、时序结果以及调试问题记录。

\par
\textbf{关键词：} ZYNQ7020；FPGA；Sobel边缘检测；UART；HDMI；BRAM；上位机
\end{abstract}

\section{实验五系统总体设计}

\subsection{系统数据流}

实验五是在 UART 图像输入和 Sobel HDMI 显示的基础上加入显示控制。系统的数据流如图 \ref{fig:system-flow} 所示。PC 上位机负责读取图片或摄像头画面，将其转换为 \verb|128 x 72| 的 RGB888 数据帧；同时，上位机也可以发送控制帧。PS 端负责串口接收与帧解析，把图像数据写入 BRAM 图像区，把显示模式、阈值和叠加开关写入 BRAM 控制区。PL 端根据 BRAM 中的数据完成图像读取、灰度转换、Sobel 边缘检测和显示输出。

这一结构的好处是 PS 和 PL 分工比较清楚。PS 端适合处理串口协议、帧头检查和控制字更新；PL 端适合做固定时序的像素读取、流水线处理和 HDMI 输出。控制信息写入 BRAM 后，PL 不需要直接处理 UART 协议，只需要读取约定地址中的控制字。

\subsection{UART 图像帧与控制帧}

图像帧仍沿用前面实验的行传输方式。每帧先发送帧头，帧头中包含宽度、高度和 RGB888 格式标记；随后逐行发送行头和像素数据。基础规格下，一帧图像包含 $128 \times 72 = 9216$ 个像素，每个像素 3 字节。

\begin{lstlisting}[language={},caption={UART 图像帧格式}]
frame header: 55 AA width_l width_h height_l height_h 18
line header : 33 CC row_l row_h
pixel data  : R G B, repeated 128 times per row
\end{lstlisting}

控制帧使用另一组同步头，与图像帧区分。实验中使用 \verb|A5 5A cmd value| 表示一次控制命令，其中 \verb|cmd=1| 表示显示模式，\verb|cmd=2| 表示阈值，\verb|cmd=3| 表示彩色叠加开关。

\begin{lstlisting}[language={},caption={UART 控制帧格式}]
control header: A5 5A
cmd = 1: display mode
cmd = 2: sobel threshold
cmd = 3: overlay enable
value: command value
\end{lstlisting}

由于图像帧和控制帧使用不同帧头，PS 端可以在同一个串口接收流程中区分数据类型。图像帧进入 BRAM 图像区，控制帧更新控制字，不会互相覆盖。

\subsection{阈值控制与彩色叠加}

阈值控制用于调节 Sobel 边缘输出的强弱。阈值较低时，弱边缘也容易被保留下来，画面中边缘较多；阈值较高时，只有强边缘被保留，画面会更干净。这个功能对演示比较重要，因为不同输入图像的亮度和对比度不同，固定阈值不一定都合适。

彩色叠加本质上是在原图 RGB 输出阶段增加一次选择：如果当前像素的 Sobel 强度超过阈值，则输出预设边缘颜色；否则输出原图像素。这样既能看到边缘，也能保留原图内容，比单独的黑白边缘图更直观。

\begin{lstlisting}[style=Verilog,caption={彩色边缘叠加逻辑示意}]
wire edge_on;
assign edge_on = (sobel_value > threshold);

always @(*) begin
    case (display_mode)
        2'd0: rgb_out = rgb_original;
        2'd1: rgb_out = {gray, gray, gray};
        2'd2: rgb_out = {edge, edge, edge};
        2'd3: rgb_out = edge_on ? EDGE_COLOR : rgb_original;
    endcase
end
\end{lstlisting}

这一段逻辑在硬件上并不复杂，但它要求前面的图像坐标、灰度流水线和 Sobel 输出都保持同步。如果延迟没有对齐，叠加边缘会相对原图偏移。因此，叠加显示也是检查整条图像流水线对齐情况的一个办法。

\section{第二周综合扩展设计}

\subsection{任务选择}

第二周综合扩展选择的是“基于 \verb|sobel_05| 的上位机与输入规格扩展”。老师给出的建议方向中包括输入来源、输入尺寸、缩放裁剪策略、PS/PL 图像尺寸适配等内容。结合实验时间和已有工程稳定性，本组实际完成的重点是上位机侧输入格式扩展：在不破坏实验五原有 FPGA 显示控制链路的前提下，让上位机支持新增图片格式输入，并在发送前统一转换为工程支持的 RGB888 图像帧。

这里采用的策略是“上位机预处理优先”。FPGA 端仍按当前工程支持的图像规格进行接收和显示；不同格式的输入图片先由 PC 端读取、解码、缩放，再通过 UART 发送。这样做的原因很直接：图片格式解析、缩放和文件读取更适合放在 PC 上位机完成；如果把这些工作放进 FPGA 或 PS 端，会明显增加开发量和调试风险。

\subsection{扩展前后对比}

\begin{table}[H]

\caption{综合扩展前后对比}

\subsection{关键代码思路}

上位机程序中对输入文件格式进行统一管理，图片读取完成后再进行尺寸处理。核心思想是：不把文件格式差异传给 FPGA，FPGA 只接收统一的 RGB888 像素帧。

\begin{lstlisting}[language=Python,caption={上位机新增图片格式支持思路}]
IMAGE_EXTENSIONS = {".png", ".jpg", ".jpeg", ".bmp"}

frame_bgr = cv2.imread(image_path, cv2.IMREAD_COLOR)
if frame_bgr is None:
    raise RuntimeError("failed to open image")

frame_bgr = scale_frame_to_target(frame_bgr, target_w, target_h)
frame_rgb = cv2.cvtColor(frame_bgr, cv2.COLOR_BGR2RGB)
send_frame_by_line(serial_port, frame_rgb)
\end{lstlisting}

缩放策略采用上位机完成。对于输入图片与目标比例不一致的情况，可以选择直接拉伸、保持比例填充或裁剪。实际演示时优先使用稳定的缩放方式，保证 FPGA 端收到的帧尺寸和工程配置一致。

\section{资源利用率、时序结果与性能分析}

\subsection{资源利用率}

\figone{0.86}{exp5_utilization.png}{实验五综合扩展资源利用率}{fig:exp5-util}

从图 \ref{fig:exp5-util} 可以看到，工程资源主要消耗在 LUT、FF 和 BRAM 上。BRAM 用于图像缓存以及 PS/PL 控制字交换；LUT 和 FF 主要用于 HDMI 时序、BRAM 读写控制、灰度转换、Sobel 计算和显示模式选择。实验五相比前面实验增加了控制通路和显示选择逻辑，因此资源占用会高于单纯 HDMI 图案显示，但仍处于 ZYNQ7020 资源范围内。

上位机输入格式扩展本身不会明显增加 FPGA 资源，因为图片解码和预处理放在 PC 侧完成。这个设计取舍比较适合课程实验：硬件侧保持稳定，输入侧灵活性由软件承担，调试成本低一些。

\subsection{时序结果}

\figone{0.86}{exp5_timing.png}{实验五综合扩展时序结果}{fig:exp5-timing}

时序分析主要关注 Setup、Hold 和 Pulse Width。实验截图显示工程可以完成综合实现并生成 bitstream，说明当前设计在实验使用的时钟约束下可以进行上板验证。实际演示中 HDMI 能够稳定输出画面，也从现象上说明像素时钟、BRAM 读取和显示控制链路能够连续工作。

需要注意的是，课程实验中的串口传输速率较低，整体帧率主要受 UART 速度限制，而不是 Sobel 计算本身。PL 端图像处理是流水线结构，一旦图像已经进入 BRAM，灰度、边缘和显示模式选择可以按像素时钟连续输出；真正耗时的是 PC 到 PS 的串口传输过程。

\subsection{性能瓶颈分析}

本系统主要瓶颈有三个：

\begin{enumerate}
    \item 串口带宽。基础图像为 $128 \times 72$，RGB888 一帧约 27 KB，加上帧头和行头后传输时间较明显。如果波特率保持 115200，刷新速度不适合高帧率视频。
    \item 上位机预处理。新增图片格式需要先解码、缩放再发送。对单张图片影响不大；若输入视频或摄像头连续帧，则上位机处理和串口发送会共同限制刷新速度。
    \item BRAM 地址和显示坐标约定。PS 写入地址、PL 读取地址和 HDMI 坐标映射必须一致，否则会出现图像错位、花屏或显示不刷新。
\end{enumerate}

从课程设计目标来看，当前性能已经能满足功能演示。若后续继续优化，可以考虑提高 UART 波特率、使用更高带宽接口，或者在 PS/PL 之间采用更完整的 DMA 图像传输方案。

\section{问题记录与处理}

\subsection{串口占用问题}

调试时最容易遇到的问题是串口被多个软件同时占用。例如上位机正在发送图像时，串口助手无法再打开同一个 COM 口；反过来，如果串口助手已经打开，上位机发送会失败。处理方法是一次只保留一个串口程序连接：需要看 PS 端打印信息时打开串口助手；需要发送图像时关闭串口助手，改用上位机程序连接。

\subsection{SDK 运行和只读工作区问题}

Vivado 导出硬件后启动 SDK 时，曾遇到工作区目录只读导致 SDK 报错的问题。后续处理方式是更换可写工作区，或者清理只读属性后再启动 SDK。PS 程序运行时，需要先确认 bitstream 已经下载到 FPGA，再在 SDK 中选择对应的应用工程运行。

\subsection{图像格式与尺寸匹配问题}

输入扩展时不能只看上位机能不能打开图片，还要看最终送给 FPGA 的帧是否满足工程约定。若帧头中的宽高、格式字段或实际像素数量不一致，PS 端可能一直等待帧头或拒绝当前帧。最终采用上位机统一预处理方案，先把不同来源的图片转成 RGB888 和目标尺寸，再通过原协议发送，避免把格式差异传到硬件侧。

\subsection{显示控制不同步问题}

显示模式、阈值和叠加开关由控制帧写入 BRAM 控制区。如果 PS 写入地址和 PL 读取地址不一致，就会出现上位机发送了控制命令但 HDMI 画面不变化的现象。因此调试时需要同时检查上位机发送日志、PS 串口打印和 PL 端地址定义，保证控制字地址约定一致。

\section{总结}

本次最终报告主要记录第二周围绕实验五展开的工作。基础部分完成了 PC 上位机、PS 程序、BRAM 缓存、PL 图像处理和 HDMI 显示之间的完整联调，实现了原图、灰度、边缘、彩色叠加显示以及阈值控制。相比前面几个实验，实验五更接近一个完整的小系统：既有图像数据通路，也有控制命令通路。

综合扩展部分选择了上位机输入扩展方向。实际实现中，本组没有盲目扩大硬件改动范围，而是把新增图片格式读取和预处理放在 PC 端完成，再将统一后的 RGB888 数据送入 FPGA。这种方案虽然不像完全改 PL 尺寸那样激进，但更稳定，也更符合当前实验基础：硬件侧复用已经跑通的 UART/BRAM/HDMI 链路，上位机侧负责输入灵活性。

通过这次实验，我们对 ZYNQ 平台中 PS 与 PL 的分工有了更具体的认识。PS 更适合协议解析和控制管理，PL 更适合稳定时序下的图像流水线处理；上位机则适合处理文件格式、图像缩放和用户交互。真正上板时，很多问题并不是某一段代码单独出错，而是协议、地址、时序和外设状态没有对齐。把这些接口逐一确认清楚，是本次课程设计最大的收获。
